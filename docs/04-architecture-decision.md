# NextERP 架构决策：微服务 vs 模块化单体

## 决策背景

在构建 NextERP 下一代ERP系统时，一个关键的架构决策是选择**微服务架构**还是**模块化单体架构**。这个决策将长期影响系统的开发效率、运维成本、性能表现和演进能力。

---

## 详细对比分析

### 1. 开发效率

| 维度 | 微服务 | 模块化单体 |
|------|--------|-------------|
| **本地开发** | 需启动多个服务，配置复杂 | 单一应用，启动简单 |
| **IDE 支持** | 跨服务跳转困难 | 完整的代码导航 |
| **调试** | 分布式追踪复杂 | 本地调试直观 |
| **测试** | 需要服务mock | 单元测试简单 |
| **代码复用** | 需要共享库 | 直接调用 |
| **构建时间** | 服务独立构建快 | 单体构建慢 |

**结论**：模块化单体在开发效率上显著优于微服务

### 2. 运维复杂度

| 维度 | 微服务 | 模块化单体 |
|------|--------|-------------|
| **部署** | 多服务协调，复杂度高 | 单一部署单元 |
| **监控** | 需要全链路监控 | 统一监控简单 |
| **日志** | 分布式日志收集 | 集中式日志 |
| **故障排查** | 需要多服务关联 | 单体排查简单 |
| **版本管理** | 多版本共存复杂 | 统一版本 |
| **回滚** | 部分回滚复杂 | 整体回滚 |
| **资源消耗** | 多JVM，内存开销大 | 单JVM，资源占用少 |

**结论**：模块化单体运维成本显著低于微服务

### 3. 性能表现

| 维度 | 微服务 | 模块化单体 |
|------|--------|-------------|
| **调用延迟** | 网络开销 (1-10ms) | 进程内调用 (<0.1ms) |
| **事务性能** | 分布式事务复杂 | 本地事务ACID |
| **序列化开销** | JSON序列化 | 无需序列化 |
| **数据库连接** | 多连接池 | 单连接池复用 |
| **缓存效率** | 分布式缓存 | 本地缓存可选 |

**结论**：模块化单体性能优于微服务

### 4. 数据一致性

```
┌─────────────────────────────────────────────────────────────────────────┐
│                      ERP 系统的数据一致性挑战                          │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  典型业务场景：销售订单 → 库存扣减 → 财务凭证                         │
│                                                                         │
│  微服务架构下的分布式事务:                                              │
│  ┌──────────────┐    ┌──────────────┐    ┌──────────────┐            │
│  │ Sales Svc    │    │ Inventory Svc│    │ Finance Svc  │            │
│  └──────────────┘    └──────────────┘    └──────────────┘            │
│         │                    │                    │                   │
│         │   1. 创建订单       │                    │                   │
│         ├───────────────────►│                    │                   │
│         │   2. 扣减库存       │                    │                   │
│         │                    ├───────────────────►│                   │
│         │   3. 生成凭证       │                    │                   │
│         │                    │                    │                   │
│         ◄────────────────────────────────────────                    │
│         4. 任何步骤失败，需要全部回滚                                 │
│                                                                         │
│  分布式事务解决方案:                                                   │
│  - Seata AT模式: 需要拦截SQL，性能损失                                 │
│  - Seata TCC模式: 需要编写补偿逻辑，复杂度高                            │
│  - Saga模式: 最终一致性，不适合强事务场景                               │
│  - 消息队列: 异步处理，一致性保证更弱                                   │
│                                                                         │
│  模块化单体下的本地事务:                                               │
│  ┌───────────────────────────────────────────────────────────────────┐  │
│  │  @Transactional                                                  │  │
│  │  public void createOrder(SalesOrder order) {                     │  │
│  │      salesService.save(order);     // 1. 创建订单                │  │
│  │      inventoryService.deduct(order); // 2. 扣减库存              │  │
│  │      financeService.createVoucher(order); // 3. 生成凭证         │  │
│  │  }                                                                │  │
│  │  // 任何步骤失败，自动回滚，ACID保证                              │  │
│  └───────────────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────────────┘
```

**结论**：ERP强事务一致性要求下，模块化单体优势明显

### 5. 扩展能力

| 维度 | 微服务 | 模块化单体 |
|------|--------|-------------|
| **水平扩展** | 精粒度扩展 | 整体扩展 |
| **独立部署** | 支持 | 不支持 |
| **技术异构** | 支持 | 不支持 |
| **故障隔离** | 好 | 差 |
| **团队独立** | 支持 | 需协调 |

**结论**：微服务在扩展性和团队隔离上占优

## ERP 系统的特殊考虑

### 1. 高度的业务关联性

```
销售订单 → 库存预留 → 发货过账 → 财务凭证 → 成本核算
    ↓         ↓          ↓           ↓           ↓
  共享主数据 (客户、物料、供应商)
```

### 2. 复杂的跨模块批量处理

| 批量场景 | 跨模块依赖 | 微服务挑战 |
|---------|-----------|-----------|
| **月末结账** | 所有财务模块 | 分布式事务、最终一致性 |
| **MRP运算** | 供应链+生产+销售 | 大量服务间调用 |
| **成本核算** | 全模块数据聚合 | 数据一致性难以保证 |

### 3. 严格的合规要求

- 会计期间必须保证数据一致性
- 审计追踪要求完整的事务记录
- 法规要求的报表生成

## 推荐方案：模块化单体

基于以上分析，NextERP 推荐**模块化单体架构**作为起点。

### 核心理由

1. **快速交付**：单一部署单元，DevOps 简单
2. **事务简化**：ERP 强事务一致性要求，本地事务更可靠
3. **成本控制**：运维成本显著低于微服务
4. **团队友好**：小团队更适合单体开发
5. **性能优势**：进程内调用，无网络开销

## 模块化单体设计原则

### 1. 模块边界清晰

```java
// 使用 ArchUnit 进行架构测试
@AnalyzeClasses(packages = "com.nexterp")
public class ArchitectureTest {

    @ArchTest
    static final ArchRule finance_module_rule =
        classes().that().resideInAPackage("..finance..")
            .should().onlyBeAccessed().byAnyPackage("..finance..", "..platform..");

    @ArchTest
    static final ArchRule supply_module_rule =
        classes().that().resideInAPackage("..supply..")
            .should().onlyDependOnClassesThat()
            .resideInAnyPackage("..supply..", "..platform..", "java..", "org.springframework..");
}
```

### 2. 模块间通信 - 接口隔离

```java
// 模块内部实现
package com.nexterp.finance.internal;

@Service
@RequiredArgsConstructor
public class FiVoucherServiceImpl implements FiVoucherService {
    // 实现细节
}

// 模块对外接口
package com.nexterp.finance.api;

public interface FiVoucherService {
    FiVoucherVO getById(Long id);
    Long create(FiVoucherCreateDTO dto);
}
```

### 3. 领域事件驱动解耦

```java
// 发布事件
@Service
@RequiredArgsConstructor
public class SalesOrderService {
    private final ApplicationEventPublisher eventPublisher;

    public void createOrder(SalesOrderCreateDTO dto) {
        SalesOrder order = buildOrder(dto);
        orderRepository.save(order);

        // 发布订单创建事件
        eventPublisher.publishEvent(new SalesOrderCreatedEvent(order.getId()));
    }
}

// 订阅事件
@Component
@RequiredArgsConstructor
public class FinanceOrderListener {
    @EventListener
    public void handleOrderCreated(SalesOrderCreatedEvent event) {
        // 财务模块处理订单创建事件
        // 生成应收账款记录等
    }
}
```

### 何时考虑拆分微服务

| 条件 | 描述 |
|------|------|
| 团队规模 | 超过 30 人，需要并行开发 |
| 性能瓶颈 | 单个模块成为系统性能瓶颈 |
| 独立部署价值 | 模块有独立的发布周期需求 |
| 技术异构 | 需要不同的技术栈 |
| 独立扩展 | 需要针对特定模块进行资源扩展 |

### 优先拆分的模块

1. **报表服务**：计算密集，独立部署不影响核心业务
2. **通知服务**：异步处理，故障不影响主流程
3. **文件服务**：可独立扩展，对接多种存储
4. **数据同步服务**：与外部系统集成，独立演进

## 总结

### 关键要点

1. **从简单开始**：模块化单体是 ERP 项目的最佳起点
2. **预留演进空间**：严格的模块边界便于未来拆分
3. **拥抱领域驱动**：DDD 设计确保模块内聚
4. **事件驱动解耦**：使用领域事件实现模块间松耦合

### 决策结论

**采用模块化单体架构，原因：**

- ✅ 开发效率高，交付速度快
- ✅ 运维成本低，团队友好
- ✅ 事务简单，数据一致性有保障
- ✅ 性能优越，网络开销小
- ✅ 预留演进路径，可持续优化

**关键设计原则：**

- 严格的模块边界（接口隔离 + ArchUnit 测试）
- 领域事件驱动模块解耦
- DDD 设计，预留拆分空间
- API 层独立（便于未来拆分）
